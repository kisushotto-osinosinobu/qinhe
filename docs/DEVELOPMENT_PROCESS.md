# 完整开发流程与验收基线

本文是青禾超市信息管理系统的执行流程和课程项目复现基线。流程参考零售 ERP、POS、进销存系统的通用领域划分，但没有复制任何闭源商业系统代码或界面。

## 1. 需求基线与完成定义

先把需求拆成可验证的业务闭环，而不是按页面数量衡量完成度：

1. 身份闭环：注册 → 登录 → 后端鉴权 → 会话撤销 → 密码修改后全端失效。
2. 商品闭环：分类 → 商品档案 → 图片 → 上下架 → 双端读取最新售价和库存。
3. 采购闭环：供应商 → 采购草稿 → 确认入库 → 库存增加 → 流水与审计可追溯。
4. 销售闭环：查商品 → 建单/预占 → 收款出库或取消释放 → 退货回补 → 统计净额。
5. 管理闭环：用户角色 → 权限矩阵 → 配置 → 审计 → CSV 导出。

每个闭环的完成定义同时包含：数据库约束、后端规则、前端交互、错误分支、自动化测试和文档。只有代码编译不能视为业务完成。

## 2. 架构与版本决策

- 后端固定 Java 17、Spring Boot 3.x、MyBatis、MySQL 8.0，采用 Controller → Service → Mapper 分层。
- Web 使用 Vue 3、TypeScript、Vite、Pinia、Vue Router 和 Element Plus。
- 小程序为独立 uni-app Vue 3 工程，构建目标固定为 `mp-weixin`，不使用移动网页冒充。
- Flyway 管理数据库结构；开发演示数据仅由 `dev` profile 加载。
- 所有依赖锁定到明确版本并提交 Maven/PNPM 锁定信息；来源与许可证记录在 `THIRD_PARTY.md`。

版本升级流程：查官方维护状态 → 检查 Java/Node/编译器兼容性 → 更新锁文件 → 执行全量测试 → 记录升级原因。禁止只改版本号不复验。

## 3. 数据库设计流程

1. 先建用户、商品、供应商、库存、采购、销售、退货、流水、配置和审计实体。
2. 金额统一 `DECIMAL`/`BigDecimal`，禁止浮点数记账。
3. 编码、条码、订单号、幂等键建立唯一约束；状态和非负库存建立检查约束。
4. 主从关系使用外键；历史销售明细保存商品名称、规格、单位和成交价快照。
5. 高频检索字段建立组合索引，例如订单状态与创建时间、会员与创建时间、流水业务来源。
6. 从空库执行迁移，再验证演示数据不会在非 `dev` 环境加载。

结构变更必须新增 Flyway 迁移，已发布迁移不得直接改写。

## 4. 后端纵向开发顺序

按风险从高到低开发真实链路：

1. 统一响应、异常处理、参数校验、分页和审计上下文。
2. 登录、BCrypt、JWT、数据库会话、注销与角色鉴权。
3. 分类、商品、供应商及图片上传。
4. 库存台账与不可重复流水。
5. 采购确认入库事务。
6. 订单预占、收款、取消和退货事务。
7. 销售统计、热销商品和防 CSV 公式注入导出。
8. 用户、角色、配置和审计管理。

Controller 只负责协议与权限；Service 负责状态转换和事务；Mapper 只执行参数绑定 SQL。客户端传入的角色、金额、价格、库存和订单状态一律不可信。

## 5. 权限与渠道建模

权限同时在路由体验和后端方法级规则执行，以后端为准。公共注册固定为 `MEMBER`。

销售创建还必须校验角色与渠道：

| 请求渠道 | 允许角色 | 行为 |
| --- | --- | --- |
| `WEB_POS` | `ADMIN`、`CASHIER` | 门店收银，可在同一事务模拟收款 |
| `MINIAPP` | `MEMBER` | 创建待付款订单并预占库存，客户端不能自行标记收款 |

库存管理员不能创建、取消或读取销售单；会员只能读取和取消本人订单。即使绕过前端按钮直接调用接口，也应得到 403。

## 6. 事务、并发与幂等

- 下单锁定库存行，只有 `current_qty - reserved_qty` 足够时才能增加预占。
- 收款锁订单和库存，在一个事务中把当前库存、预占库存同时扣减。
- 取消只允许待付款状态，并在同一事务释放预占。
- 采购确认锁采购单，重复确认直接返回已入库结果。
- 退货锁订单和销售明细，累计退货不得超过销售数量，成功后回补当前库存。
- 订单、退货和库存流水使用唯一业务键；数据库唯一约束是并发情况下的最后防线。

并发测试至少包含两线程争抢最后一个可售库存，断言只产生一个成功订单且库存永不为负。

## 7. Web 开发流程

1. 建立登录态、Axios 拦截、路由守卫和角色菜单。
2. 优先完成登录 → 商品 → 库存 → POS → 订单 → 统计主链。
3. 再完善供应商、采购、系统管理、个人资料和密码。
4. 所有列表提供分页或有界查询，表单提供前端提示并保留服务端最终校验。
5. 危险业务动作显示影响说明并二次确认；真实支付没有接入时始终标记“模拟收款”。
6. 适配常用桌面宽度和窄屏，提供加载态、空状态和错误提示。

## 8. 微信小程序开发流程

1. 小程序复用同一后端和 MySQL，只保存 Token、用户信息和本地购物车。
2. 页面进入、下拉刷新或提交业务后重新读取服务端数据。
3. 商品详情、购物车、下单、本人订单、取消、资料、密码、员工库存均调用真实 API。
4. 小程序订单显式声明 `MINIAPP`；员工账号只用于授权业务查询，不能伪装会员下单。
5. 开发者工具导入目录是 `miniapp/dist/build/mp-weixin`，其中必须存在 `project.config.json`。
6. 模拟器验证商品页、登录、购物车、订单、个人中心、员工库存，并读取 Console/Network 证据。
7. 真机前替换真实 AppID，将 API 部署到备案 HTTPS 域名并加入微信合法域名。

若实现微信身份登录，必须使用服务端真实 `code2Session`，AppSecret 只能保存在服务器密钥配置中。本项目当前使用账号密码联调，不伪造微信授权。

## 9. 测试流水线

本地执行顺序：

1. 创建空 MySQL 8.0 测试库。
2. `mvn -B clean verify`：编译、单元测试、Flyway、MySQL 集成测试。
3. Web 执行 `pnpm typecheck`、`pnpm test`、`pnpm build`。
4. 小程序执行 `pnpm typecheck`、`pnpm build:mp-weixin`。
5. 启动后端和 Web，完成真实浏览器关键路径。
6. 导入微信开发者工具，完成模拟器编译、网络和控制台检查。
7. 提交并推送，等待 GitHub Actions 的 `backend`、`clients` 作业均成功。

测试报告严格区分“通过、失败、未执行、被外部条件阻塞”，保留首次失败、根因和复验记录。

## 10. 安全与交付检查

- 扫描 `.env`、Token、AppSecret、私钥、数据库数据目录和构建垃圾。
- 生产配置强制从环境变量读取数据库口令和 JWT 密钥。
- 校验 `.gitignore`、锁文件、迁移、README、API、数据库、权限、同步和测试文档齐全。
- 禁止强制推送；远端有历史时先拉取、比较和合并。
- 推送后通过 GitHub API 核对远端 SHA、根目录内容和 Actions 结果。
- 最终报告同时列出完成项、未执行项、启动方法、提交 SHA 和外部条件。

## 11. 后续商业化演进

课程范围之外可按优先级增加：多门店/仓库、批次和保质期、采购退货、销售促销、会员积分、交接班、打印小票、消息通知和真实支付。引入这些能力前必须先扩展领域模型、权限矩阵、迁移和测试，不能只增加界面按钮。
